NTLM logs in Microsoft Sentinel

Where Windows records NTLM authentication, how to turn each log on, how it gets into Sentinel, what the events contain, and the KQL to search them.

Checked against Microsoft documentation on 19 October 2026.

The short version

Where NTLM gets logged
The Security log on every machine (4624, 4625, 4776); the Microsoft-Windows-NTLM/Operational log once NTLM auditing is on (8001–8006, their blocked twins 4001–4006, and the newer 4020–4033); and Defender for Identity and Defender for Endpoint, if you run them.
How it reaches Sentinel
The Windows Security Events via AMA connector ships the Security log to SecurityEvent. The NTLM/Operational log needs its own data collection rule and lands in Event or WindowsEvent. Defender data arrives through the Defender XDR connector as IdentityLogonEvents and DeviceLogonEvents.
The trap
The 8001–8007 IDs in the connector’s Common and Minimal event sets are AppLocker events, not NTLM. And neither set includes 4776.
Best single event
8004 on domain controllers: the account, the client machine and the server it signed in to, all in one record. Start there.
New this month
The 13 October 2026 updates bring enhanced NTLM auditing to Windows Server 2019 and 2022. They also make blocking of NTLMv1-derived single sign-on the default on Windows 11 24H2+ and Server 2025 machines without Credential Guard, unless BlockNtlmv1SSO says otherwise.

1Turn on the logging

Set these with Group Policy (or the Intune settings catalog), then confirm on one machine before you build pipelines. Defaults differ between Windows versions and security baselines, so set everything explicitly.

Security log audit policy

Computer Configuration › Policies › Windows Settings › Security Settings › Advanced Audit Policy Configuration › Audit Policies

SubcategorySet toApply toEvents
Logon/Logoff › Audit LogonSuccess and FailureEvery machine that accepts network logons4624, 4625
Account Logon › Audit Credential ValidationSuccess and FailureDomain controllers; member machines too if you care about local accounts4776

Also set Audit: Force audit policy subcategory settings (Windows Vista or later) to override audit policy category settings to Enabled, so legacy category settings can’t override these.

NTLM audit policies

Computer Configuration › Policies › Windows Settings › Security Settings › Local Policies › Security Options

PolicyValueApply toWrites to NTLM/Operational
Network security: Restrict NTLM: Outgoing NTLM traffic to remote servers Audit all All machines, DCs included 8001 on the machine that starts NTLM
Network security: Restrict NTLM: Audit Incoming NTLM Traffic Enable auditing for domain accounts (member servers); Enable auditing for all accounts (DCs, as Defender for Identity asks) Servers and DCs 8003 for domain accounts; with “all accounts”, also 8002 for local accounts and loopback
Network security: Restrict NTLM: Audit NTLM authentication in this domain Enable all Domain controllers only 8004, 8005, 8006

The registry values behind them, for checking or for Intune: RestrictSendingNTLMTraffic and AuditReceivingNTLMTraffic under HKLM\SYSTEM\CurrentControlSet\Control\Lsa\MSV1_0, and AuditNTLMInDomain under HKLM\SYSTEM\CurrentControlSet\Services\Netlogon\Parameters.

Audit, don’t block. The same list holds the blocking settings: Outgoing NTLM set to Deny all, Incoming NTLM traffic, and NTLM authentication in this domain. Those stop sign-ins. Once anything is blocked, Windows logs 4001–4006 instead of 8001–8006.

Enhanced NTLM auditing

Newer Windows writes a richer set of events to the same log: who used NTLM, why Kerberos wasn’t used, and where it went, including target IP, SPN and NTLM version.

  • Available on Windows 11 24H2 and later and Windows Server 2025, and on Windows Server 2019 and 2022 with the updates released on or after 13 October 2026 (KB5126651 and KB5126655).
  • On by default. Client and server events are controlled by Administrative Templates › System › NTLM › NTLM Enhanced Logging; domain-wide events on DCs by Administrative Templates › System › Netlogon › Log Enhanced Domain-wide NTLM Logs. If you can’t see these settings, update the ADMX files in your central store.
  • They don’t replace 8001–8006. With both enabled, both log.

If you run Defender for Identity

Defender for Identity needs 4776 and 8004 on DCs anyway, and it can configure them for you.

  • Sensor v3.x on Windows Server 2019 or later: in the Defender portal go to Settings › Identities › Advanced features and turn on Automatic Windows auditing configuration. The sensor applies the audit and NTLM settings locally and rechecks every 24 hours. GPOs that set the same values can conflict with it.
  • Sensor v2.x, or automatic auditing off: use the GPOs above or the DefenderForIdentity PowerShell module.
PowerShell
# Report what is configured today (Domain mode reads your GPOs)
New-MDIConfigurationReport -Path 'C:\Reports' -Mode Domain -Identity 'CONTOSO\gmsaMDI$' -OpenHtmlReport

# Create and link GPOs with every setting Defender for Identity needs
Set-MDIConfiguration -Mode Domain -Configuration All

Check one machine

PowerShell
# Audit policy in effect
auditpol /get /subcategory:"Logon"
auditpol /get /subcategory:"Credential Validation"

# NTLM audit settings in effect (AuditNTLMInDomain exists on DCs only)
Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Lsa\MSV1_0' |
    Select-Object RestrictSendingNTLMTraffic, AuditReceivingNTLMTraffic
Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Services\Netlogon\Parameters' |
    Select-Object AuditNTLMInDomain

# Newest NTLM events, then the log's size and retention
Get-WinEvent -LogName 'Microsoft-Windows-NTLM/Operational' -MaxEvents 20 |
    Format-Table TimeCreated, Id, LevelDisplayName -AutoSize
wevtutil gl Microsoft-Windows-NTLM/Operational

On busy DCs, raise the log size so events survive while the agent is down, for example wevtutil sl Microsoft-Windows-NTLM/Operational /ms:268435456 for 256 MB.

2Get it into Sentinel

Windows collection runs on the Azure Monitor Agent (AMA) and data collection rules (DCRs). Machines outside Azure need Azure Arc first. Don’t build on the legacy Log Analytics agent; it was retired on 31 August 2024.

Decide what to collect where

MachineSecurity logNTLM/OperationalWhat it buys you
Domain controllers4776, plus 4624 and 46258004–8006, 4030–4033, 4004–4006Nearly all domain-account NTLM, with the target server, from a handful of machines
Member servers4624, 46258002, 8003, 4022/4023Source IP, NTLM version and the server process
WorkstationsUsually not needed8001, 4020/4021, 4024/4025, on targeted machinesWhich process starts NTLM, and why

Start with DCs. Add servers when you need IPs and versions, and target workstations when you’re chasing a specific fallback.

Security log to SecurityEvent

  1. In Content hub, install the Windows Security Events solution and open the Windows Security Events via AMA connector.
  2. Create a data collection rule and add your machines.
  3. Pick an event set. Common covers 4624, 4625 and 4768 (one of the queries below uses 4768). All events takes everything in the Security and AppLocker logs and costs the most.
  4. For DCs, add a second rule set to Custom for what Common leaves out:
XPath
Security!*[System[(EventID=4776 or EventID=4769)]]

4769 (Kerberos service tickets) is only needed for the NTLM-versus-Kerberos trend query. Keep the XPath of different rules from overlapping, or the same event is ingested twice.

If cost forces it, you can collect only NTLM logons from servers, instead of (not alongside) an event set that already includes 4624. Test an XPath locally first with Get-WinEvent -LogName Security -FilterXPath '…', leaving off the Security! prefix.

XPath
Security!*[System[(EventID=4624)] and EventData[Data[@Name='AuthenticationPackageName']='NTLM']]

NTLM/Operational to Event or WindowsEvent

The connector won’t collect this log, so create a DCR yourself. Each line below is a separate XPath entry.

From the portal, landing in Event. Azure portal › Monitor › Data Collection Rules › Create. Choose Windows, add the machines, then Add data source › Windows Event Logs › Custom, enter the XPath, and send it to your Sentinel workspace.

XPath, everything
Microsoft-Windows-NTLM/Operational!*
XPath, smaller rule for DCs
Microsoft-Windows-NTLM/Operational!*[System[(EventID>=8004 and EventID<=8006)]]
Microsoft-Windows-NTLM/Operational!*[System[(EventID>=4030 and EventID<=4033)]]
Microsoft-Windows-NTLM/Operational!*[System[(EventID>=4004 and EventID<=4006)]]

From ARM, Bicep or the REST API, landing in WindowsEvent. Use the Microsoft-WindowsEvent stream. EventData then arrives as a parsed dynamic column, so EventData.SChannelName just works, and WindowsEvent supports the Auxiliary/data lake tier, which Event doesn’t. Afterwards, associate the rule with your machines on the DCR’s Resources page.

DCR body (JSON)
{
  "location": "<region>",
  "properties": {
    "dataSources": {
      "windowsEventLogs": [
        {
          "name": "ntlmOperational",
          "streams": [ "Microsoft-WindowsEvent" ],
          "xPathQueries": [ "Microsoft-Windows-NTLM/Operational!*" ]
        }
      ]
    },
    "destinations": {
      "logAnalytics": [
        { "name": "sentinel", "workspaceResourceId": "<workspace resource ID>" }
      ]
    },
    "dataFlows": [
      { "streams": [ "Microsoft-WindowsEvent" ], "destinations": [ "sentinel" ] }
    ]
  }
}
PowerShell, test an XPath on the machine
Get-WinEvent -LogName 'Microsoft-Windows-NTLM/Operational' -FilterXPath '*[System[(EventID=8004)]]' -MaxEvents 5

Defender for Identity and Defender for Endpoint

  • With Sentinel onboarded to the Defender portal, you can query IdentityLogonEvents and DeviceLogonEvents in Advanced hunting next to your Sentinel tables. Nothing needs copying for the 30 days advanced hunting keeps.
  • To keep them longer, or to use them in workspace analytics rules, stream them with the Microsoft Defender XDR connector (Connect events, then tick the tables). The schema matches advanced hunting. The connector itself is switched on automatically when you onboard to the Defender portal; streaming raw events is a separate choice.
  • Defender for Identity only sees NTLM that reaches the DCs it monitors. Local-account NTLM never shows up there.

Windows Event Forwarding instead of agents everywhere

Subscribe the NTLM/Operational channel (and any Security events you want) on a Windows Event Collector, install the agent there, and use the Windows Forwarded Events connector. Everything lands in WindowsEvent. Built-in analytics written for SecurityEvent won’t see forwarded Security events, so adapt them or keep the Security log on the AMA connector.

Volume and cost

Every NTLM pass-through a DC handles writes an 8004, and 4624 is already one of the biggest event IDs in most workspaces. Measure before widening collection (see the ingestion volume query in section 4). Your levers:

  • XPath filters at the source. Cheapest, because the data never leaves the machine.
  • Ingestion-time transformations. SecurityEvent, Event and WindowsEvent all support them.
  • The Auxiliary/data lake tier for SecurityEvent and WindowsEvent, for long-retention inventory data you don’t alert on.

NTLM/Operational: classic audit events

These date back to Windows 7 and Server 2008 R2. Each has a blocked twin that’s logged instead once a Restrict NTLM policy denies the attempt.

Event (blocked)Logged onMeaningWhat you get
8001 (4001)ClientOutgoing NTLM from this machineTarget server or SPN, supplied user and domain, client process name and PID, the process’s identity
8002 (4002)ServerIncoming NTLM the machine validates itself: local accounts, loopbackThe calling process and its identity
8003 (4003)Member serverIncoming NTLM with a domain accountUser, domain, client workstation, server process (for example w3wp.exe), logon type
8004 (4004)DCPass-through from a member server over its secure channelSecure channel name (the server accessed), user, domain, workstation (the client), secure channel type
8005 (4005)DCNTLM sign-in directly to the DC, such as a network logon to the DC itselfSimilar to 8004
8006 (4006)DCPass-through from a trusted domain over a secure channelSimilar to 8004

In the raw XML, 8004’s fields are SChannelName, UserName, DomainName, WorkstationName and SChannelType, which is what the queries below use. For the other IDs, run the field explorer query to see the exact names in your data.

To follow one sign-in across machines, Microsoft’s own method is to line up the DC’s 8004, the server’s 8003 (that server is the 8004’s secure channel name) and the client’s 8001 (that client is the 8004’s workstation) on account name and time.

4Search

Run these in Sentinel’s Logs, or in Advanced hunting in the Defender portal once your workspace is onboarded. Time windows are starting points. The NTLMv1 and DC-account queries make good scheduled analytics rules; map the Account, Host and IP entities.

Is NTLM data arriving?

Tables: SecurityEvent, Event, WindowsEvent

Run this first. Tables you don’t have are skipped.

KQL
// NTLM-related events that reached the workspace in the last 24 hours
union isfuzzy=true
    (SecurityEvent
        | where TimeGenerated > ago(24h) and EventID in (4624, 4625, 4776)
        | extend Log = "Security"),
    (Event
        | where TimeGenerated > ago(24h) and EventLog == "Microsoft-Windows-NTLM/Operational"
        | extend Log = "NTLM/Operational"),
    (WindowsEvent
        | where TimeGenerated > ago(24h) and Channel == "Microsoft-Windows-NTLM/Operational"
        | extend Log = "NTLM/Operational")
| summarize Events = count(), Machines = dcount(Computer), LastSeen = max(TimeGenerated)
    by Table = Type, Log, EventID
| order by Table asc, EventID asc

NTLM logons by server and version

Table: SecurityEvent (4624)

Which servers still accept NTLM, how much, and which version.

KQL
// NTLM network logons per server, split by NTLM version
SecurityEvent
| where TimeGenerated > ago(7d)
| where EventID == 4624 and AuthenticationPackageName == "NTLM"
| where TargetUserName != "ANONYMOUS LOGON"
| summarize Logons = count(),
            Accounts = dcount(TargetAccount),
            SourceIPs = dcount(IpAddress)
    by Server = Computer, LmPackageName, LogonType
| order by Logons desc

NTLMv1 and LM logons

Table: SecurityEvent (4624)

The list to clear before you refuse NTLMv1. Anonymous sessions are left out because they always report NTLM V1.

KQL
// NTLMv1 and LM logons, excluding anonymous sessions
SecurityEvent
| where TimeGenerated > ago(30d)
| where EventID == 4624 and AuthenticationPackageName == "NTLM"
| where LmPackageName == "LM" or LmPackageName startswith "NTLM V1"
| where TargetUserName != "ANONYMOUS LOGON"
| summarize Logons = count(),
            FirstSeen = min(TimeGenerated),
            LastSeen = max(TimeGenerated),
            SourceIPs = make_set(IpAddress, 25),
            ClaimedClients = make_set(WorkstationName, 25)
    by Server = Computer, Account = TargetAccount, LmPackageName
| order by Logons desc

Top NTLM accounts seen by DCs

Table: SecurityEvent (4776)

A baseline from DC logs alone: which accounts lean on NTLM, and from how many clients.

KQL
// NTLM "top talkers" as seen by domain controllers
SecurityEvent
| where TimeGenerated > ago(7d)
| where EventID == 4776
| summarize Validations = count(),
            Failures = countif(Status !~ "0x0"),
            Clients = dcount(Workstation),
            SampleClients = make_set(Workstation, 10)
    by Account = TargetUserName
| top 25 by Validations

NTLM share of DC authentications over time

Table: SecurityEvent (4776, 4769)

A progress chart for an NTLM reduction project. Needs 4776 and 4769 collected (see section 2).

KQL
// Daily NTLM validations as a percentage of NTLM + Kerberos service tickets.
// 4769 counts service tickets, so read this as a trend, not an exact ratio.
SecurityEvent
| where TimeGenerated > ago(30d)
| where EventID in (4776, 4769)
| summarize NTLM = countif(EventID == 4776), Kerberos = countif(EventID == 4769)
    by Day = bin(TimeGenerated, 1d)
| extend NTLMPercent = round(100.0 * NTLM / (NTLM + Kerberos), 1)
| project Day, NTLMPercent
| render timechart

Password spray over NTLM, DC view

Table: SecurityEvent (4776)

One client failing for many accounts. The client name is whatever the attacker sent, so pivot to 8004 for the target server and to that server’s 4625 for the real IP.

KQL
// Many accounts failing NTLM validation from one claimed client in 15 minutes
SecurityEvent
| where TimeGenerated > ago(1d)
| where EventID == 4776 and Status !~ "0x0"
| summarize Failures = count(),
            Accounts = dcount(TargetUserName),
            Codes = make_set(Status, 10)
    by ClaimedClient = Workstation, Window = bin(TimeGenerated, 15m)
| where Accounts >= 10
| order by Accounts desc

Failed NTLM logons by source IP

Table: SecurityEvent (4625)

Brute force and spray against servers, with the source address the server actually saw.

KQL
// Failed NTLM network logons on servers, grouped by source IP
SecurityEvent
| where TimeGenerated > ago(1d)
| where EventID == 4625 and AuthenticationPackageName == "NTLM"
| summarize Failures = count(),
            Accounts = dcount(TargetUserName),
            Servers = dcount(Computer),
            SubStatuses = make_set(SubStatus, 10),
            ClaimedNames = make_set(WorkstationName, 10)
    by IpAddress
| where Failures >= 20
| order by Accounts desc

DC computer accounts signing in with NTLM

Table: SecurityEvent (4624, 4768)

Rare in a healthy domain, and a classic sign of coerced authentication being relayed. Check whether the source IP really belongs to that DC.

KQL
// Build the list of DC computer accounts from machines that log 4768 (only DCs do)
let DCAccounts = SecurityEvent
    | where TimeGenerated > ago(1d) and EventID == 4768
    | distinct Computer
    | project Account = strcat(toupper(tostring(split(Computer, ".")[0])), "$");
SecurityEvent
| where TimeGenerated > ago(1d)
| where EventID == 4624 and LogonType == 3 and AuthenticationPackageName == "NTLM"
| where toupper(TargetUserName) in (DCAccounts)
| project TimeGenerated, TargetHost = Computer, TargetUserName,
          IpAddress, WorkstationName, LmPackageName

Where NTLM is still used, from 8004

Table: Event (NTLM/Operational 8004)

Every server that receives pass-through NTLM, with its users and clients. This is your remediation list.

KQL
// Servers receiving NTLM pass-through, from DC event 8004
Event
| where TimeGenerated > ago(7d)
| where EventLog == "Microsoft-Windows-NTLM/Operational" and EventID == 8004
| extend Server = extract(@"Name=.SChannelName.>([^<]*)", 1, EventData),
         User   = extract(@"Name=.UserName.>([^<]*)", 1, EventData),
         Domain = extract(@"Name=.DomainName.>([^<]*)", 1, EventData),
         Client = extract(@"Name=.WorkstationName.>([^<]*)", 1, EventData)
| summarize Auths = count(),
            Users = dcount(User),
            Clients = dcount(Client),
            SampleUsers = make_set(strcat(Domain, "\\", User), 10)
    by Server
| order by Auths desc

The same map from WindowsEvent

Table: WindowsEvent (NTLM/Operational 8004)

If your DCR uses the Microsoft-WindowsEvent stream, the fields are already parsed.

KQL
// Servers receiving NTLM pass-through, WindowsEvent version
WindowsEvent
| where TimeGenerated > ago(7d)
| where Channel == "Microsoft-Windows-NTLM/Operational" and EventID == 8004
| extend Server = tostring(EventData.SChannelName),
         User   = strcat(tostring(EventData.DomainName), "\\", tostring(EventData.UserName)),
         Client = tostring(EventData.WorkstationName)
| summarize Auths = count(), Users = dcount(User), Clients = dcount(Client)
    by Server, DC = Computer
| order by Auths desc

Explore the fields of any NTLM event

Tables: Event, WindowsEvent

Turns each event’s XML into a property bag, so you can see the exact field names before writing a parser.

KQL, Event table
// Every field of recent NTLM/Operational events as a property bag
Event
| where TimeGenerated > ago(1d)
| where EventLog == "Microsoft-Windows-NTLM/Operational"
| extend Data = parse_xml(EventData).DataItem.EventData.Data
| mv-apply d = Data on (
    summarize Fields = make_bag(bag_pack(tostring(d["@Name"]), tostring(d["#text"])))
  )
| project TimeGenerated, Computer, EventID, EventLevelName, Source, Fields
| take 50
KQL, WindowsEvent table
WindowsEvent
| where TimeGenerated > ago(1d)
| where Channel == "Microsoft-Windows-NTLM/Operational"
| project TimeGenerated, Computer, EventID, EventLevelName, Provider, EventData
| take 50

Why clients fall back to NTLM

Table: Event (NTLM/Operational 4020, 4021)

Groups the enhanced client events by reason, process and target. It reads the rendered message; if RenderedDescription is empty in your data, use the field explorer and read EventData instead.

KQL
// Reasons, processes and targets behind NTLM fallback
Event
| where TimeGenerated > ago(7d)
| where EventLog == "Microsoft-Windows-NTLM/Operational" and EventID in (4020, 4021)
| extend Reason  = extract(@"Reason:\s*([^\r\n]+)", 1, RenderedDescription),
         Process = extract(@"Process Name:\s*([^\r\n]+)", 1, RenderedDescription),
         Target  = extract(@"Target Machine:\s*([^\r\n]+)", 1, RenderedDescription)
| summarize Events = count(), Machines = dcount(Computer) by Reason, Process, Target
| order by Events desc

NTLM security downgrades

Table: Event (NTLM/Operational 4021, 4023, 4031, 4033)

The Warning-level enhanced events: NTLMv1, missing MIC or no Extended Protection. Same rendered-message caveat as above.

KQL
// Machines reporting downgraded NTLM, with the versions and MIC status seen
Event
| where TimeGenerated > ago(7d)
| where EventLog == "Microsoft-Windows-NTLM/Operational"
| where EventID in (4021, 4023, 4031, 4033)
| extend NtlmVersion = extract(@"NTLM Version:\s*([A-Za-z0-9]+)", 1, RenderedDescription),
         MIC         = extract(@"MIC Status:\s*([A-Za-z]+)", 1, RenderedDescription)
| summarize Events = count(), Versions = make_set(NtlmVersion), MICStatus = make_set(MIC)
    by Computer, EventID
| order by Events desc

NTLM being blocked

Tables: Event (4001–4006, 4025), SecurityEvent (4625)

Watch these as you enforce Restrict NTLM policies, and since the October 2026 NTLMv1 single sign-on change.

KQL, NTLM/Operational
// Blocked by Restrict NTLM policies (4001-4006) or NTLMv1-derived SSO blocking (4025)
Event
| where TimeGenerated > ago(7d)
| where EventLog == "Microsoft-Windows-NTLM/Operational"
| where EventID between (4001 .. 4006) or EventID == 4025
| summarize Events = count(), LastSeen = max(TimeGenerated) by Computer, EventID
| order by Events desc
KQL, Security log
// Failed logons where NTLM was refused by policy
SecurityEvent
| where TimeGenerated > ago(7d)
| where EventID == 4625 and SubStatus =~ "0xc0000418"
| summarize Failures = count() by Computer, TargetAccount, IpAddress, WorkstationName
| order by Failures desc

NTLM across normalized sources

Parser: _Im_Authentication (ASIM)

One query over every authentication source with an ASIM parser. Results depend on each parser filling LogonProtocol.

Traps

  • Same IDs, different logs. AppLocker also uses 8001–8007, and those are the ones in the connector’s event sets. Filter on the channel (EventLog or Channel), never on the ID alone.
  • The provider isn’t the channel. DC-side events such as 8004 and 4030–4033 are written by Security-Netlogon into the NTLM/Operational channel. Filter on the channel.
  • Missing from the event sets. Common and Minimal include neither 4776 nor 4769.
  • 4776 lives where the account lives. DC-only collection never sees local-account NTLM; that 4776 is on the member machine.
  • Anonymous isn’t NTLMv1. ANONYMOUS LOGON sessions report NTLM V1 because there’s no key material. Microsoft says to ignore them for version reporting.
  • Workstation names are claims. WorkstationName and Workstation come from the client, and spray tools fake or randomize them. Prefer IpAddress, but remember NAT and relay hosts.
  • Padded values. LogonProcessName often carries a trailing space (NtLmSsp ). Use has, not ==.
  • System, PID 4. NTLM through kernel-mode components (SMB client and server, and HTTP.sys behind IIS, WinRM and ADWS) shows up as System, so the process field won’t name the app.
  • Loopback noise. Auditing incoming NTLM for all accounts records machines authenticating to themselves, often for RPC Endpoint Mapper.
  • Expected NTLM. Vulnerability scanners probe with it, external trusts default to it, and MS-CHAPv2 (NPS, Wi-Fi, VPN) depends on NTLM-derived credentials.
  • Version reporting can mislead. Microsoft documents a 4624 that said NTLM V1 while a network trace showed NTLMv2, with a third-party SMB client. Confirm with 4022/4032 or a trace before blaming a device.
  • DCs still accept NTLMv1. Server 2025 can’t start NTLMv1 itself, but a Server 2025 DC still validates NTLMv1 passed through to it. Keep watching DC-side events.
  • Forwarded events change tables. Security events forwarded through WEF land in WindowsEvent, not SecurityEvent.

What’s changing

  1. October 2023Microsoft announces it will retire NTLM.
  2. Windows 11 24H2 and Server 2025The NTLMv1 protocol is removed. NTLMv1-derived credentials linger in MS-CHAPv2 single sign-on.
  3. July 2025Microsoft documents enhanced NTLM auditing (4020–4033) for Windows 11 24H2 and Server 2025.
  4. August to November 2025Auditing of NTLMv1-derived single sign-on (4024) reaches Windows 11 24H2+, then Server 2025.
  5. January 2026Microsoft publishes a three-phase plan to disable NTLM by default. Phase 1, the enhanced auditing, is available on Windows 11 24H2 and Server 2025.
  6. Second half of 2026Phase 2, as planned: IAKerb and a local KDC to remove common reasons for falling back to NTLM, with core Windows services preferring Kerberos.
  7. 13 October 2026Enhanced auditing comes to Server 2019 and 2022. Where BlockNtlmv1SSO isn’t set and Credential Guard is off, NTLMv1-derived single sign-on is now blocked and logged as 4025. Check MS-CHAPv2 Wi-Fi, Ethernet and VPN.
  8. 31 March 2027Sentinel leaves the Azure portal and is only available in the Defender portal.
  9. Next major Windows Server releasePhase 3: network NTLM disabled by default, in Windows Server and the matching client versions. It can be re-enabled through policy.

To allow NTLMv1-derived single sign-on temporarily, set BlockNtlmv1SSO to 0 under HKLM\SYSTEM\CurrentControlSet\Control\Lsa\MSV1_0. Microsoft treats this as a short-term exception, not a fix.

Next steps once you can see it

  • End NTLMv1 and LM. When the NTLMv1 query stays empty, set Network security: LAN Manager authentication level to Send NTLMv2 response only. Refuse LM & NTLM.
  • Turn on Credential Guard where the hardware allows. Microsoft recommends it, and it already protects against NTLMv1-derived credentials.
  • Put admins in Protected Users. Members can’t use NTLM at all.
  • Fix the fallback causes the reason IDs point to: duplicate SPNs (setspn -X), access by IP address, missing SPNs, and clients without line of sight to a DC.
  • Block in small steps. Start with outgoing NTLM on Tier 0 and privileged access workstations, new servers, and the SMB client on Windows 11 24H2 and Server 2025, using exception lists for stragglers.
