Palo Alto Traffic Split

Change plan · Sentinel syslog collectors

Split Palo Alto traffic between the data lake and analytics

Today the traffic DCR writes every traffic log to PaloAltoTraffic_CL as parsed fields, plus the full original line in RawData and its file path in FilePath. After this change the same DCR sends each log two ways: the parsed fields go to PaloAltoTraffic_CL in the analytics tier, and the original line goes to a new data lake tier table, PaloAltoTrafficRaw_CL. Nothing changes on the collectors.

What changes

TableTierTodayAfter the change
PaloAltoTraffic_CLexisting Analytics Parsed fields (SourceIP, Action, Bytes …), Computer, RawData, FilePath Parsed fields and Computer only. RawData and FilePath stay empty.
PaloAltoTrafficRaw_CLnew Data lake Doesn't exist TimeGenerated, Computer, RawData for every traffic log

In both tables Computer is the firewall's name, taken from the log file name. Every log lands in both tables. A Sentinel split rule works differently: it moves whole rows to the lake. This plan splits the columns instead.

1

Check what reads RawData

Open Cloud Shell in Bash mode (in PowerShell mode, type bash first) and set these. If Cloud Shell restarts later, run this block again.

bash
RG=alp-rg-sentinel-prod-01
WS=alp-law-sentinel-prod-01
DCR=alp-dcr-sentinel-prod-01-linux-collector-pan-traffic
RAW=PaloAltoTrafficRaw_CL
SUB=$(az account show --query id -o tsv); echo "$SUB"

The ID printed must be the Sentinel subscription. If it isn't, run az account set --subscription <ID> and run the block again.

Analytics rules that use PaloAltoTraffic_CL

bash
# One line per analytics rule that queries PaloAltoTraffic_CL
az rest --method get --url "/subscriptions/$SUB/resourceGroups/$RG/providers/Microsoft.OperationalInsights/workspaces/$WS/providers/Microsoft.SecurityInsights/alertRules?api-version=2025-09-01" \
  | jq -r '.value[] | select((.properties.query // "") | test("PaloAltoTraffic_CL")) | "\(.properties.displayName)  |  uses RawData: \(.properties.query | test("RawData"))"'

A rule that shows uses RawData: true stops matching once RawData is empty. Change it to use the parsed columns before step 4, or tell me which field it needs and I'll add it to the parser. If your rules go through a parser function rather than the table name, check that function too. Check workbooks and saved hunting queries on this table by hand.

How much of the table is RawData today

In Logs:

kql
PaloAltoTraffic_CL
| where TimeGenerated > ago(1d)
| summarize TotalGB = round(sum(_BilledSize) / 1e9, 2),
            RawDataGB = round(sum(estimate_data_size(RawData)) / 1e9, 2),
            FilePathGB = round(sum(estimate_data_size(FilePath)) / 1e9, 2)

RawDataGB plus FilePathGB is roughly what leaves the analytics tier each day. About RawDataGB a day goes to the lake instead.

2

Create the lake table

Create the table with the CLI, then move it to the data lake tier before any data reaches it.

bash
az monitor log-analytics workspace table create -g "$RG" --workspace-name "$WS" -n "$RAW" \
  --plan Analytics --columns TimeGenerated=dateTime Computer=string RawData=string
  • In the Defender portal, go to Microsoft Sentinel → Configuration → Tables, select PaloAltoTrafficRaw_CL and choose Manage table.
  • Select Data lake tier, set the retention (30 days to 12 years, for example 365 days) and save.

Then check it:

bash
# Expect plan Auxiliary and the retention you set
az monitor log-analytics workspace table show -g "$RG" --workspace-name "$WS" -n "$RAW" \
  --query "{table:name, plan:plan, retentionDays:totalRetentionInDays}" -o table

Expect Auxiliary as the plan. That's Azure Monitor's name for the lake tier. If Manage table doesn't offer Data lake tier, the workspace isn't onboarded to the Sentinel data lake; stop here and tell me.

A table can't be renamed, and its tier can change only once a week, so check the name before you save.

3

Build and test the new DCR

Back up the DCR and print its current data flow:

bash
DCR_ID=$(az resource list -n "$DCR" --resource-type Microsoft.Insights/dataCollectionRules --query "[0].id" -o tsv); echo "$DCR_ID"
az rest --method get --url "$DCR_ID?api-version=2023-03-11" > pan-traffic-dcr-backup.json
jq -r '.properties.dataFlows[] | "== \(.streams[0]) -> \(.outputStream)\n\(.transformKql)\n"' pan-traffic-dcr-backup.json

Expect one flow, Custom-Text-PaloAltoTraffic_CL -> Custom-PaloAltoTraffic_CL, with RawData, FilePath in its project line. If it looks different, stop and send me the output.

Build the new version and preview it. Nothing is deployed yet:

bash
jq --arg out "Custom-PaloAltoTraffic_CL" --arg raw "Custom-$RAW" '
  ([.properties.dataFlows[] | select(.outputStream == $out)]
     | if length == 1 then .[0] else error("expected 1 flow to \($out), found \(length)") end) as $f
  | .properties.dataFlows |= (
      map(if .outputStream == $out then .transformKql += "\n| project-away RawData, FilePath" else . end)
      + [{ streams: $f.streams,
           destinations: $f.destinations,
           transformKql: "source\n| project TimeGenerated, Computer = extract(@\"([^/]+)\\.log$\", 1, FilePath), RawData",
           outputStream: $raw }])
' pan-traffic-dcr-backup.json > pan-traffic-dcr-new.json
# Preview both flows as they will be deployed
jq -r '.properties.dataFlows[] | "== \(.outputStream)\n\(.transformKql)\n"' pan-traffic-dcr-new.json
# Must end with: OK, only dataFlows changed
diff <(jq -S 'del(.properties.dataFlows)' pan-traffic-dcr-backup.json) <(jq -S 'del(.properties.dataFlows)' pan-traffic-dcr-new.json) && echo "OK, only dataFlows changed"
  • Flow 1 is your existing parser with one line added at the end, | project-away RawData, FilePath. FilePath goes too because it only repeats the firewall name that's already in Computer. To keep it, delete , FilePath from that line in the command.
  • Flow 2 is new: the same input, three columns, into PaloAltoTrafficRaw_CL.
  • The last line must print OK, only dataFlows changed.
  • Keep pan-traffic-dcr-backup.json until you're happy with the change. It's your rollback.

Test flow 2 on real rows

PaloAltoTraffic_CL still holds RawData and FilePath, so you can run flow 2's query on today's data in Logs. Expect firewall names in Computer and full log lines in RawData:

kql
PaloAltoTraffic_CL
| where TimeGenerated > ago(1h)
| take 20
| project TimeGenerated, Computer = extract(@"([^/]+)\.log$", 1, FilePath), RawData

Flow 1's parser doesn't change, so it needs no test.

4

Deploy

Only do this once step 2 shows the lake tier, so that no raw data lands in the analytics tier.

bash
# Expect: Succeeded
az rest --method put --url "$DCR_ID?api-version=2023-03-11" --body @pan-traffic-dcr-new.json --query properties.provisioningState -o tsv

If the command fails, nothing has changed; send me the error. If it succeeds, note the time. The collectors need nothing: the change is in how Azure routes the data they already send. It usually takes effect within minutes, but allow up to an hour.

5

Verify

Analytics table: parsed fields only

In Logs, 30 minutes after deploying. Expect WithRawData to be 0 and Parsed to equal Rows:

kql
PaloAltoTraffic_CL
| where TimeGenerated > ago(15m)
| summarize Rows = count(), WithRawData = countif(isnotempty(RawData)), Parsed = countif(isnotempty(SourceIP))

Lake table: lines arriving

In the Defender portal, go to Microsoft Sentinel → Data lake exploration → KQL queries and select the workspace. New data shows up there about 15 minutes after it arrives.

kql
PaloAltoTrafficRaw_CL
| where TimeGenerated > ago(1h)
| summarize Rows = count(), Firewalls = dcount(Computer), Latest = max(TimeGenerated)

Both tables: same row count

Once 90 minutes have passed since the deploy, run this in Data lake exploration. The two counts should match:

kql
union withsource = SourceTable PaloAltoTraffic_CL, PaloAltoTrafficRaw_CL
| where TimeGenerated between (ago(90m) .. ago(30m))
| summarize Rows = count() by SourceTable

DCR health

In the Azure portal, open the DCR and select Metrics. Logs Transform Errors per Min and Logs Rows Dropped per Min should stay at 0. Logs Ingestion Bytes Out (Uncompressed), split by DestinationTable, shows how much goes to each table.

Roll back

Put the backup back. PaloAltoTraffic_CL gets RawData and FilePath again, and the lake table stops receiving data. If Cloud Shell has restarted, run the block in step 1 and the DCR_ID= line in step 3 first.

bash
# Expect: Succeeded
az rest --method put --url "$DCR_ID?api-version=2023-03-11" --body @pan-traffic-dcr-backup.json --query properties.provisioningState -o tsv

After this

  • Older rows in PaloAltoTraffic_CL keep their RawData until their retention ends. The empty RawData and FilePath columns can stay in the table, since empty columns cost nothing.
  • Data in the lake tier can't drive analytics rules or alerts. Query it in Data lake exploration, where queries are slower and billed per query, or use a KQL job to copy a slice back into the analytics tier for an investigation.
  • Cost: the lake tier charges a processing fee on all traffic data sent to it, plus lake ingestion and storage. Parsing into PaloAltoTraffic_CL has no transformation charge, because Sentinel is enabled on the workspace.
  • The same split works for PaloAltoThreat_CL and the URL logs when you want it.
